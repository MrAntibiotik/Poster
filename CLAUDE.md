# Poster — правила проєкту

## ❗ Головне: мінімум запитів до Instagram і Facebook (Meta Graph API)

Зайві запити до Meta шкодять публікаціям: після них Instagram/Facebook починають відмовляти
(ліміти, «ProcessingFailedError», зависання контейнерів). Тому **кожен запит до Meta має бути виправданий**.

- Перш ніж додати будь-який запит до Graph API / rupload — перевірити, чи не можна взяти дані з бази
  (`post_stats`, `account_stats`, kv) або зробити це рідше. Нові періодичні перевірки — лише з кешем і великим інтервалом.
- **Статистики з Instagram/Facebook немає взагалі** (видалено з коду: `_MetaBase.get_stats/get_views/account_stats`
  повертають порожнє без запитів). Аналітика — лише YouTube. Не повертати без прямого прохання користувача.
- **Публікація Instagram — одна логіка для всіх шляхів** (`Publisher._publish_instagram`, `Instagram.publish` /
  `upload_only` / `wait_inline` / `finish_container`, фон — `Publisher.finish_instagram` → `_ig_check`):
  один контейнер — одне очікування. Статуси (`container_state`): FINISHED → media_publish; IN_PROGRESS / PENDING /
  невідомий → чекати ТОЙ САМИЙ контейнер; ERROR / EXPIRED → лише тоді наступний спосіб (`Instagram.methods_for`:
  оригінал, якщо сумісний → копія під вимоги Reels → легка 30 к/с; 720p не використовувати); PUBLISHED → знайти
  опублікований, не публікувати вдруге; помилка media_publish → повтор того самого контейнера (до 3 разів).
  **Тайм-аут — НЕ помилка Meta**: нового контейнера через час очікування не створювати ніколи. Єдиний виняток —
  «файл не дійшов»: rupload 400 і GET rupload показує offset 0 (`upload_lost`) — після `lost_retry_after_min` (30 хв)
  нове завантаження того самого відео через 30 хв, ще одне через 60 хв, далі — у Telegram (`Publisher._ig_lost`).
  Підстава — історія: завислі контейнери не оживали ніколи, а нове завантаження пізніше проходило (#54, #55, #63);
  дубля бути не може — у старому контейнері 0 байтів.
  ID контейнера пишеться в базу одразу після створення (`on_container`) — перезапуск не завантажує відео вдруге.
  Звичайний режим: перші 10 хв перевірки 10/20/40/80 с, далі фон 2/5/10/20/40 хв → раз на 3 год → остання після 24 год
  (~13 запитів за добу на контейнер); якщо й тоді не готовий — як EXPIRED (інший спосіб або вручну).
  «Тихий» (`silent_wait`): перша перевірка через `wait_min` (20 хв), далі так само.
- Тривалість: офіційні межі Reels API 3 с – 15 хв (`media.ig_duration_problem`) — поза ними контейнер не створюється.
  **Рішення користувача: шортси до 60 с — копія для Instagram обрізається до 59,5 с** (`platforms.instagram.max_seconds`,
  `media.ig_max_seconds`; 0 — не обрізати). Оригінал не змінюється; довший за межу — лише копією. Межу «понад 55 с —
  лише вручну» прибрано. `IG_COPY_VERSION` змінювати, коли змінюється спосіб копіювання. `IG_TARGET_MB` (45) — внутрішнє
  налаштування Poster, не вимога Meta.
- Відмова без контейнера (тривалість, файл, створення контейнера) або після всіх способів — повне відео користувачу
  в Telegram (`_ig_to_phone`, `platforms.instagram.fallback_manual`), а не ❌.
- В Instagram — одне завантаження за раз (`ig_wait`); контейнер, що обробляється довше `block_max_min` (60 хв), чергу
  більше не тримає (сам чекає далі), а НАСТУПНІ відео публікуються автоматично як завжди — НЕ вручну (користувач
  прямо відкинув ідею «поки висить одне — решта вручну»). Користувачу — одне повідомлення про затримку (без запиту
  до Meta) й кнопка «📱 Не чекати».
- Після перезапуску/оновлення перевірка доступів не повторюється, якщо була < 12 год тому.
- Щоденний тест Instagram (`maybe_ig_watch`) — не частіше ніж раз на 48 год; `/igcheck …` — лише за запитом користувача
  (кожен тест створює контейнери — нагадувати про це).
- Обмеження Meta (коди 4/17/32/613/80001+) → `RateLimited`: не стукати до кінця вікна (`blocked_until`).

## Історія публікацій (для аналізу)

- Кожна спроба кожного відео на кожній платформі пишеться в таблицю `history` (`app/insights/history.py`, `record`):
  результат, тривалість/розмір/к/с/бітрейт файлу, спосіб, HTTP і ПОВНА відповідь завантаження (debug_info),
  status_code/status контейнера, УСІ перевірки статусу з часом (`polls`), x-fb-trace-id / x-fb-debug, звук, етап, де
  зламалось, і категорія проблеми (`containers.category`: файл / завантаження / обробка Meta / media_publish), час, помилка. Вивантаження — `/history`
  у боті (підсумок + CSV) і панель → Журнал. Новий шлях публікації чи новий результат — обов'язково записувати сюди.

- Журнал контейнерів Instagram (`app/insights/containers.py`): на кожен контейнер — блок «Instagram container:» (ID, тривалість,
  розмір, кодек, роздільність, к/с, бітрейт надісланого файлу, Upload completed, Last status_code/status/error_message,
  Processing time, Result) у log.txt і data/ig_containers.jsonl; у боті — /containers. Пишеться в `_save_diag` і `Publisher._hist`.

## Інше

- Користувач спілкується українською; відповіді — українською, просто й по суті.
- Програма на ПК користувача сама оновлюється з `main` — усе, що потрапляє в `main`, за кілька хвилин працює в нього.
  Тому перед пушем: `python -m pyflakes app tests`, `python -m unittest discover -s tests -q`.
- Реліз: підняти `VERSION` у `config.py`, запис зверху в `CHANGELOG.md`, `python tools/make_releases.py`, коміт, пуш у `main`.
- Ніколи не комітити `.env`, `config.json`, `tokens/`, `client_secret.json`, токени. Токени користувач вводить лише в панелі.
- Токени не мають потрапляти в журнал: `setup_logging` ховає їх (`redact`, `SECRET_PATTERNS` у `app/core/config.py`),
  сторонні бібліотеки (oauthlib, requests) — лише WARNING. Новий тип ключа — додати шаблон.
- Дані каналів: `channels/main`, `channels/en` (див. `app/core/layout.py`).
